# Elecraft DXF reliability design

Status: design boundary approved in conversation; written-spec review pending. 2026-10-18.

## Goal and boundary

Make DXF Open → ordinary edit → Save/Save As → reopen safe against silent loss of represented content and against overwriting another writer's changes. This is the second milestone of `2026-10-17-elecraft-windows-cad-design.md`, after the synthetic Windows baseline at `c335196b0b8e54f70299484c88a59bd1becdddd0`. It does not promise lossless support for every DXF producer or version. It does not implement the PostgreSQL registry, DWG/native `.drw`/`.mdb` fidelity, or Elecraft MSI packaging.

The work occurs on `feat/elecraft-dxf-reliability` in `/opt/data/agent/elecraft-dxf-reliability`, based on the Windows-baseline branch. CADMATIC installations, `UserData`, and native project originals are not fixtures and remain untouched. No real user drawing is modified during validation.

## Existing boundaries and observed gap

`cadcraft-io` decodes/encodes DXF (`read_dxf`, `write_with`) and preserves modeled and some raw records. `cadcraft-engine::cmd::file` owns the shared native `open`, `qsave`, and `saveas` path; desktop UI and headless command/control routes use that path. `ReadFile`/`read_bytes` do not retain source-byte identity. Native `store` writes a fixed `<path>.cadcraft-tmp` and calls `std::fs::rename`, without candidate reopen/semantic comparison, external-change detection, or verified Windows replacement/recovery. Existing engine autosave and UI Drawing Recovery are separate mechanisms and must be audited rather than assumed to solve safe publication. The web download path cannot verify the recipient's filesystem and is not part of the native overwrite guarantee.

## Approach and components

1. **Permission-cleared corpus and baseline audit.** Acquire a small, varied set of third-party DXFs from public primary sources with an explicit license permitting local test use. Record source URL, retrieval date, exact license URL/text or source attribution, SHA-256, format/version, size, redistribution conditions, and expected feature/dependency inventory. Refuse files with uncertain terms or personal data. Store original bytes and dependent assets under a private, agent-accessible corpus outside the Git repository, for example `/opt/data/agent/docs/elecraft/dxf-corpus/`; do not commit or publish them. A checked-in metadata/test contract may refer to fixture IDs and checksums but never include private bytes, unlicensed content, or absolute personal paths. Tests run only when a fixture is present and its pinned hash matches; the required local/Windows compatibility gate fails or reports **not run**, never silently substitutes synthetic files. Keep separately authored, small synthetic DXFs in the repo for deterministic edge/failure cases. Record expected results per fixture as **preserve**, **read-only/block overwrite**, or **reject on open**, based on independently inspected content, not merely Elecraft's own roundtrip.
2. **Read-time evidence.** On native DXF path open, capture source bytes' SHA-256, canonical path and relevant file identity/metadata, original format/version, entity/object/handle inventory, retained raw/unknown records, and unresolved dependencies (fonts, xrefs, images and other external paths). Bound file size, parse work and inventory traversal; malformed/unsupported input fails visibly before it becomes a saveable empty drawing. Preserve a private per-open baseline attached to the drawing state, including enough evidence to explain why a save is unsafe. Opening from bytes without a path remains an unsaved document; SVG/DWG follow their existing paths and are not silently placed under the DXF overwrite contract.
3. **Semantic candidate verification.** Before any native DXF overwrite, serialize the edited drawing into a unique candidate in the destination directory, flush it, reopen *those candidate bytes*, and compare the intended edited drawing and untouched source obligations with the reopened document and raw records. Compare geometry and placement with explicit numeric tolerances, entity properties, layers, text, blocks and references, handles where identity matters, ownership/xdata/extension dictionaries and retained unknown data. Declare allowed differences for the requested edit, supported version conversion, handle normalization, and writer-generated bookkeeping; do not globally ignore a category or use entity counts as a proxy. Detect dangling references and unresolved dependency changes. Produce a bounded, actionable discrepancy report with record/handle/field identifiers and a loss-risk classification; failure leaves original bytes and in-memory unsaved state intact. The comparator itself needs mutation tests that prove removal/change of a non-counted property blocks overwrite.
4. **Conflict and publication.** Record a full source-content hash at open. Immediately before publishing, reread the target and compare identity/content; a changed, missing or inaccessible source is a conflict, not permission to overwrite. Save As to an existing different target also checks for concurrent changes after its initial target read. A same-directory unique candidate is never presented as the published file. Implement a Windows-aware replacement with a recoverable prior version and verified rollback path rather than assuming `std::fs::rename` overwrites an existing Windows file. Preserve the backup until the published file can be reopened and the intended content checked; retain a recoverable version across interruption/restart under a documented retention policy. If filesystem or UNC semantics cannot provide the required conflict/recovery guarantee, refuse overwrite with a specific error; do not downgrade silently. Serialize concurrent saves to the same target within Elecraft and check external changes again as close to replacement as the platform permits. Because an independent writer can race a hash check, document and test the platform-specific exclusion/replace strategy and never claim a cross-process atomic compare-and-swap that is not evidenced. Only after successful publication update `saved`, title, path and source fingerprint; any error leaves the document dirty and its original association intact. Do not delete or modify arbitrary pre-existing `<path>.cadcraft-tmp` files.
5. **Explicit lossy export.** If preservation cannot be proved, normal Save and Save As to the source or any existing file are blocked. A user-requested lossy DXF export must require a new path, a displayed discrepancy summary and explicit acceptance. It must use exclusive new-file creation and must not mark the original drawing saved or replace its path. No automatic fallback to export. CLI/control and GUI surface the same errors; web downloads remain clearly outside the native overwrite guarantee.
6. **Recovery and dependency behavior.** Exercise current desktop autosave, Drawing Recovery, AUDIT and RECOVER with the new save contract. A crash/interruption leaves either an intact original or an identifiable prior version and an unsaved/recoverable edit; recovery tests reopen actual artifacts after a simulated restart. Opening a file with missing external fonts/xrefs/images reports which references are unresolved and their rendering impact, and preserves their references through save if supported; an unresolved dependency is not mislabeled as a complete rendering. Direct DXF open/save works without PostgreSQL.

## Acceptance matrix

- **Corpus:** at least two distinct, permission-cleared third-party DXFs from independently documented sources and multiple synthetic fixtures; one fixture with a nontrivial geometry/property/block/text mix and one with external or unknown content. If no suitable licensed real fixtures can be obtained, the real-corpus gate remains blocked. Record baseline inventory and explicit expected classification per file before relying on the gate.
- **Preservation:** on each preserve-class fixture, make a specified, bounded edit on a disposable copy, save, reopen and independently compare unaffected and edited geometry, properties, text, layers, blocks/references and retained unknown data. A deliberately corrupted candidate (same entity count but changed property, dropped xdata or dangling reference) must be rejected without changing the original hash; a read-only-class fixture must refuse ordinary overwrite with a useful reason.
- **Publication/conflicts:** exercise normal overwrite, Save As to new/existing path, an externally modified target, concurrent saves, locked/read-only file, candidate write/flush/reopen failure, interruption around replacement, recovery after restart, and missing/lost UNC path. Check the original or recoverable prior version by reopening it and checking SHA-256/semantics; no success claim from an exit code alone. Do not change production shares or access controls for tests. If a safe UNC test share is unavailable, mark that gate blocked rather than infer it from a local path.
- **Dependencies and UI:** validate dependency warnings and retained references on copies; GUI save/error/recovery and command/control paths report the same decision. An explicitly accepted lossy export creates only a new file and leaves the source and dirty state intact. Web delivery and non-DXF formats remain regression-tested for their existing behavior, not granted a DXF safety claim.
- **Platform gates:** first run focused Rust/Python fixture checks with executable local Cargo target storage, then Linux workspace tests with the existing GPU-dependent failure reported separately, and finally the native Windows unfiltered workspace/Clippy/build plus filesystem failure matrix and interactive GUI. Source hashes must match between worktree and Windows Documents copy before a Windows result is attributed to a commit. Do not run an Elecraft MSI/installer without separate authorization.

## Delivery sequence and stop rules

Implement as separately reviewed increments: (1) corpus/provenance and red baselines, (2) semantic comparison and dependency/risk reports, (3) native candidate verification and conflict-aware publication, (4) recovery/UI/headless and Windows failure matrix. Each increment has tests that fail for the intended behavior before code changes, a small commit, and independent review. If a real fixture reveals unsupported data, classify it and block overwrite; do not weaken the comparator or alter the fixture to manufacture a pass. Stop before a production file operation, broader network/share change, proprietary file use, or installer execution. The release gate remains open until both licensed real-file and Windows failure-matrix checks actually pass.
