# Elecraft DXF reliability design

Status: design boundary approved in conversation; independent written-spec review returned revisions required. Revised specification awaits user review; no implementation authorized by this document. 2026-10-18.

## Goal and boundary

Make DXF Open → ordinary edit → Save/Save As → reopen safe against silent loss of represented content and against overwriting another writer's changes. This is the second milestone of `2026-10-17-elecraft-windows-cad-design.md`, after the synthetic Windows baseline at `c335196b0b8e54f70299484c88a59bd1becdddd0`. It does not promise lossless support for every DXF producer or version. It does not implement the PostgreSQL registry, DWG/native `.drw`/`.mdb` fidelity, or Elecraft MSI packaging.

The work occurs on `feat/elecraft-dxf-reliability` in `/opt/data/agent/elecraft-dxf-reliability`, based on the Windows-baseline branch. CADMATIC installations, `UserData`, and native project originals are not fixtures and remain untouched. No real user drawing is modified during validation.

## Existing boundaries and observed gap

`cadcraft-io` decodes/encodes DXF (`read_dxf`, `write_with`) and preserves modeled and some raw records. `cadcraft-engine::cmd::file` owns the shared native `open`, `qsave`, and `saveas` path; desktop UI and headless command/control routes use that path. `ReadFile`/`read_bytes` do not retain source-byte identity. Native `store` writes a fixed `<path>.cadcraft-tmp` and calls `std::fs::rename`, without candidate reopen/semantic comparison, external-change detection, or verified Windows replacement/recovery. Existing engine autosave and UI Drawing Recovery are separate mechanisms and must be audited rather than assumed to solve safe publication. The web download path cannot verify the recipient's filesystem and is not part of the native overwrite guarantee.

## Approach and components

1. **Permission-cleared corpus and baseline audit.** Acquire a small, varied set of third-party DXFs from public primary sources with an explicit license permitting local test use. Record source URL, retrieval date, exact license URL/text or source attribution, SHA-256, format/version, size, redistribution conditions, and expected feature/dependency inventory. Refuse files with uncertain terms or personal data. Store original bytes and dependent assets under a private, agent-accessible corpus outside the Git repository, for example `/opt/data/agent/docs/elecraft/dxf-corpus/`; do not commit or publish them. A checked-in metadata/test contract refers to fixture IDs, source and dependency hashes, independent expected inventories, classifications, and license scope for download, internal transfer to the Windows test PC, dependent assets, and redistribution; it never includes private bytes, unlicensed content, or absolute personal paths. Tests run only when every required fixture and dependent asset is present with its pinned hash. The compatibility gate emits pass/fail/blocked per fixture ID, commit, platform and hashes; missing or unlicensed fixtures are **blocked**, not synthetic substitutes, and blocked cannot satisfy the release gate. Keep separately authored, small synthetic DXFs in the repo for deterministic edge/failure cases. Record expected results per fixture as **preserve**, **read-only/block overwrite**, or **reject on open**, based on independently inspected content, not merely Elecraft's own roundtrip.
2. **Read-time evidence.** On native DXF path open, capture source bytes' SHA-256, canonical path and relevant file identity/metadata, original format/version, entity/object/handle inventory, retained raw/unknown records, and unresolved dependencies (fonts, xrefs, images and other external paths). Bound file size, parse work and inventory traversal; malformed/unsupported input fails visibly before it becomes a saveable empty drawing. Before labeling the drawing saveable, independently enumerate bounded source tags/records and reconcile each relevant source entity, object and reference with the modeled, raw-retained, or explicitly skipped reader result. Every source entity, object, property or reference not represented or retained, including an explicitly skipped one, blocks all ordinary Save/Save As unless a narrowly specified transformation demonstrably preserves that obligation in the reopened candidate. If a trustworthy document cannot be constructed, **reject on open**; otherwise classify it **read-only/block ordinary save** with a reason. A reader warning, skip count or candidate roundtrip agreement cannot waive this gate. Attach the immutable source evidence and risk classification to each opened document state at the shared native DXF read boundary so both worker and command OPEN routes receive it. RECOVER must never acquire ordinary overwrite eligibility by bypassing this boundary. Keep source obligations distinct from xref geometry loaded after opening; xref load/reload must not erase the baseline. Opening from bytes without a path remains an unsaved document without source overwrite rights until an independently verified normal save; SVG/DWG follow their existing paths and are not silently placed under the DXF overwrite contract.
3. **Semantic candidate verification.** Before any native DXF overwrite, serialize the edited drawing into a unique candidate in the destination directory, flush it, reopen *those candidate bytes*, and compare the intended edited drawing and untouched source obligations with the reopened document and raw records. Compare geometry and placement with explicit numeric tolerances, entity properties, layers, text, blocks and references, handles where identity matters, ownership/xdata/extension dictionaries and retained unknown data. Use a dedicated fail-closed whole-drawing comparator, not the existing UI-oriented `COMPARE` command. Define a per-property/version comparison policy: exact text, layer, ownership, handle links, xdata, extension dictionaries and unknown/raw records unless the specified edit authorizes a change; numeric geometry uses documented field-specific absolute/relative tolerances and no blanket category exclusion. An authorized edit is identified by its affected objects/fields, not by any change to the drawing. A count, traversal, normalization or report-size overflow is an explicit blocked save, with a bounded summary, never a pass. Detect dangling references and unresolved dependency changes. Produce a bounded, actionable discrepancy report with record/handle/field identifiers and a loss-risk classification; failure leaves original bytes and in-memory unsaved state intact. Mutation tests must reject same-count property changes, deleted xdata, layout/ownership/unknown-object loss, dangling block references, and unsupported version conversions.
4. **Conflict and publication.** Record a full source-content hash at open. Immediately before publishing, reread the target and compare identity/content; a changed, missing or inaccessible source is a conflict, not permission to overwrite. Before any ordinary Save As, resolve case variants, reparse points/symlinks and hard-link identity to decide whether the destination aliases the opened source; ambiguity is a conflict, not a new file. A new target is created exclusively; an existing target requires initial identity/hash capture and a final conflict check under the same publication policy as the source. A same-directory unique candidate is never presented as the published file. Implement a Windows-aware replacement with a recoverable prior version and verified rollback path rather than assuming `std::fs::rename` overwrites an existing Windows file. Preserve the backup until the published file can be reopened and the intended content checked; retain a recoverable version across interruption/restart under a documented retention policy. If filesystem or UNC semantics cannot provide the required conflict/recovery guarantee, refuse overwrite with a specific error; do not downgrade silently. Serialize concurrent saves to the same target within Elecraft and check external changes again as close to replacement as the platform permits. Because an independent writer can race a hash check, document and test the platform-specific exclusion/replace strategy and never claim a cross-process atomic compare-and-swap that is not evidenced. Only after successful publication update `saved`, title, path and source fingerprint; any error leaves the document dirty and its original association intact. Do not delete or modify arbitrary pre-existing `<path>.cadcraft-tmp` files.
5. **Explicit lossy export.** If preservation cannot be proved, all ordinary DXF Save and Save As operations are blocked, including Save As to a new path; no operation may mark an unproved drawing saved. A user-requested lossy DXF export must require a new path, a displayed discrepancy summary and explicit acceptance. It must use exclusive new-file creation and must not mark the original drawing saved or replace its path. No automatic fallback to export. CLI/control and GUI surface the same errors; web downloads remain clearly outside the native overwrite guarantee.
6. **Recovery and dependency behavior.** Exercise current desktop autosave, Drawing Recovery, AUDIT and RECOVER with the new save contract. A process crash/interruption on a filesystem class admitted by the publication proof leaves either an intact original or an identifiable prior version; power-loss durability is a separate filesystem-class gate and must not be claimed where unproven. Unsaved edits are recoverable only if a validated autosave/recovery artifact exists, and otherwise their loss is explicitly reported. Recovery tests reopen actual artifacts after a simulated restart. Opening a file with missing external fonts/xrefs/images reports which references are unresolved and their rendering impact, and preserves their references through save if supported; an unresolved dependency is not mislabeled as a complete rendering. Direct DXF open/save works without PostgreSQL.

## Publication proof and interruption contract

An identity/hash recheck alone does not exclude an external writer. Before enabling ordinary overwrite on a Windows filesystem class (local NTFS and an explicitly disposable SMB/UNC share are separate classes), demonstrate a concrete Windows handle/share-mode and replacement protocol that excludes incompatible writers throughout the final check, backup and replacement, or return **unsupported publication semantics** without overwriting. Evaluate `CreateFileW` share modes, file IDs/final paths, `ReplaceFileW`/equivalent replacement and the share server's actual behavior together; merely naming one of these APIs is not proof they compose. Never assert cross-process atomic compare-and-swap. If exclusion cannot coexist with recoverable replacement for a class, that class remains blocked; document any residual race and do not claim the original is protected against it. Test a separate writer positioned between the final check and replacement, aliases, open handles/locks and loss of a disposable UNC share. No production share or access-control changes are part of this gate.

The transaction records an identifiable per-save operation and target/backup/candidate hashes in a recovery manifest. On a supported filesystem, flush candidate data; create and durably record the recoverable prior version and manifest before replacing an existing target; publish; reopen the actual target and compare bytes/semantics; then record completion. Include containing-directory durability where supported, and refuse or explicitly classify unsupported power-loss guarantees. Before replacement, an error leaves the target unchanged and the document dirty; after replacement but before successful verification, never report success: attempt verified rollback from the prior version, retain both artifacts and an **ambiguous publication** error if rollback cannot be proved. A restart scans only validated owned manifests, checks hashes, distinguishes pending/verified/ambiguous state, and offers recovery without silently replacing either version. Keep a prior version at least until explicit user acknowledgement of verified recovery or a documented retention/cleanup policy; no cleanup may discard the sole known-good version. Recovery of the prior on-disk drawing and recovery of unsaved in-memory edits are separate guarantees: the latter requires a valid autosave artifact and must be reported unavailable otherwise. Fault injection covers candidate creation/write/flush/reopen, backup/manifest flush, replacement, published-file verification, rollback, directory durability and restart at every phase.

## Stored dependency paths and upstream intake

Saved xref/data-link paths are untrusted drawing content; resolving/loading them is distinct from retaining their references in DXF and from paths explicitly selected by a user. Define and test a bounded trusted-path policy for local Windows and same-share UNC, with visible refusal reasons and rendering impact for cross-share/remote/device paths, symlinks/reparse escapes, nested xrefs, fallback-by-filename ambiguity and byte-budget exhaustion. An unresolved resource must not be presented as fully loaded or silently redirected to a different file. Evaluate CADCraft upstream `8fe7c421` and its `craft-docpath` dependency selectively against Elecraft's source snapshot before any adoption; the read-only audit is `docs/elecraft/upstream-audit-2026-10-18.md`. Other upstream control and drawing-command changes are independent candidates, not a wholesale merge or a substitute for this save-safety design.

## Acceptance matrix

- **Corpus:** at least two distinct, permission-cleared third-party DXFs from independently documented sources and multiple synthetic fixtures; one fixture with a nontrivial geometry/property/block/text mix and one with external or unknown content. If no suitable licensed real fixtures can be obtained, the real-corpus gate remains blocked. Record baseline inventory and explicit expected classification per file before relying on the gate.
- **Preservation:** on each preserve-class fixture, make a specified, bounded edit on a disposable copy, save, reopen and independently compare unaffected and edited geometry, properties, text, layers, blocks/references and retained unknown data. A deliberately corrupted candidate (same entity count but changed property, dropped xdata or dangling reference) must be rejected without changing the original hash; a read-only-class fixture must refuse ordinary overwrite with a useful reason.
- **Publication/conflicts:** exercise normal overwrite, Save As to new/existing path, an externally modified target, concurrent saves, locked/read-only file, candidate write/flush/reopen failure, interruption around replacement, recovery after restart, and missing/lost UNC path. Check the original or recoverable prior version by reopening it and checking SHA-256/semantics; no success claim from an exit code alone. Do not change production shares or access controls for tests. If a safe UNC test share is unavailable, mark that gate blocked rather than infer it from a local path.
- **Dependencies and UI:** validate dependency warnings and retained references on copies; GUI save/error/recovery and command/control paths report the same decision. An explicitly accepted lossy export creates only a new file and leaves the source and dirty state intact. Web delivery and non-DXF formats remain regression-tested for their existing behavior, not granted a DXF safety claim.
- **Platform gates:** first run focused Rust/Python fixture checks with executable local Cargo target storage, then Linux workspace tests with the existing GPU-dependent failure reported separately, and finally the native Windows unfiltered workspace/Clippy/build plus filesystem failure matrix and interactive GUI. Source hashes must match between worktree and Windows Documents copy before a Windows result is attributed to a commit. Do not run an Elecraft MSI/installer without separate authorization.

## Delivery sequence and stop rules

Implement as separately reviewed increments: (1) corpus/provenance and red baselines, (2) semantic comparison and dependency/risk reports, (3) native candidate verification and conflict-aware publication, (4) recovery/UI/headless and Windows failure matrix. Each increment has tests that fail for the intended behavior before code changes, a small commit, and independent review. If a real fixture reveals unsupported data, classify it and block overwrite; do not weaken the comparator or alter the fixture to manufacture a pass. Stop before a production file operation, broader network/share change, proprietary file use, or installer execution. The release gate remains open until both licensed real-file and Windows failure-matrix checks actually pass.
